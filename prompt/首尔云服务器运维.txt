## 二、 Web 网页端与 API 服务 (Nginx 统一接管)

本模块包含 **Alpha 加密页面 (`crypto`)**、**带单检测页面 (`copy-sweep`)**，以及 **极简惠选商城 (`easy-shop`)** 与其后端服务。

### 1. 整体架构 (多子域名分发)

* **链路走向:** 用户访问不同子域名 ➔ Cloudflare (仅 CDN/HTTPS) ➔ Nginx (服务器80端口) ➔ 对应前端目录或本地后端。
* **Nginx 路由规则:**
  * **前端 `crypto`:** 匹配根目录，返回 `/var/www/alpha-web/`，API 请求转发至本地 `8000` 端口。
  * **前端 `copy-sweep`:** 匹配根目录，返回 `/var/www/copy-sweep-web/`，API 请求转发至本地 `8000` 端口。
  * **全栈 `easy-shop`:** 匹配全站路由，全部反向代理至本地 **`8001` 端口**（FastAPI 统管前端静态文件与 `/api/` 接口；Nginx 独立配置并内置了核心高危接口限流防刷保护，防止官方拉黑 PID）。



### 2. 核心文件与配置路径

| 模块 | 文件/目录路径 | 维护场景说明 |
| --- | --- | --- |
| **Alpha 前端代码** | `/var/www/alpha-web/` | `crypto` 域名的静态文件存放处 |
| **Sweep 前端代码** | `/var/www/copy-sweep-web/` | `copy-sweep` 域名的静态文件存放处 |
| **Python 共享后端** | `/root/alpha-api/alpha_api.py` | 修改 AI 提示词、业务逻辑、接口处理（运行于 `8000` 端口） |
| **Alpha/Sweep Nginx 配置** | `/etc/nginx/sites-available/alpha-momentum` | 统一管理 `crypto` 与 `copy-sweep` 的前端路由及接口转发 |
| **Alpha/Sweep 系统服务** | `/etc/systemd/system/alpha-api.service` | 修改后端运行端口或环境变量 |
| **极简惠选商城代码** | `/root/easy_shop_web/mobile_web/` | 商城全栈源码目录（启动入口 `run.py`） |
| **商城核心私有配置** | `/root/easy_shop_web/mobile_web/config.local.json` | **商城唯一真相源**：修改端口 (8001)、拼多多凭据、Mongo 认证与日志等级 |
| **商城独立 Nginx 配置** | `/etc/nginx/sites-available/easy-shop` | 商城专属反向代理与核心接口限流防护规则（软链至 `sites-enabled`） |
| **商城系统服务** | `/etc/systemd/system/easy-shop.service` | 商城后台常驻与开机自启服务（运行于 `8001` 端口） |

### 3. 标准运维与通用部署流程

🟢 **通用前端网页更新 (Vite 打包部署标准 4 步)**
所有前端页面的更新，请将下方命令中的 `<对应目录>` 替换为实际路径：

1. 本地打包：`npm run build`
2. 清空旧代码：`rm -rf /var/www/<对应目录>/*`
3. 上传新代码：将本地 `dist` 文件夹内的**所有内容**上传至 `/var/www/<对应目录>/`
4. 修复文件权限：

```bash
chown -R www-data:www-data /var/www/<对应目录>
chmod -R 755 /var/www/<对应目录>
```

🟢 **Alpha 后端逻辑更新 (代码修改后必做)**
修改了 `alpha_api.py` 后，必须重启服务并检查日志：

```bash
systemctl restart alpha-api.service
journalctl -u alpha-api.service -n 50 -f
# 按 Ctrl+C 退出
```

🟢 **极简惠选商城运维与更新 (`easy-shop`)**
cd /root/easy_shop_web
git pull origin main

systemctl restart easy-shop


* **修改配置（一站式管理）：**
  只需直接编辑私有配置文件即可，无需动任何代码：
  ```bash
  nano /root/easy_shop_web/mobile_web/config.local.json
  ```
* **服务重启 / 停止 / 查看状态:**
  ```bash
  systemctl restart easy-shop.service
  systemctl stop easy-shop.service
  systemctl status easy-shop.service
  ```
* **查看实时日志与访问流水:**
  ```bash
  journalctl -u easy-shop.service -n 50 -f
  # 或查看持久化运行日志
  tail -n 100 -f /root/easy_shop_web/mobile_web/runtime/logs/mobile_web.log
  ```
* **无损自检（测试数据库连通性，不发外部网络请求）:**
  ```bash
  /root/easy_shop_web/mobile_web/venv/bin/python /root/easy_shop_web/mobile_web/run.py --check-mongo
  ```

🔵 **Nginx 配置重载 (改路由/域名/防护规则后必做)**

```bash
nginx -t
systemctl reload nginx
```

## 三、 自动交易机器人运维手册 (Grid / Martin / Signal)

当前服务器运行着 **3 套独立的交易策略机器人**，统一存放于 `/root/trader_bot` 目录下，并使用虚拟环境运行以隔离依赖。

### 1. 核心路径说明

* **核心工作目录:** `/root/trader_bot`
* **Python 虚拟环境路径:** `/root/trader_bot/venv/bin/python`
* **Grid 策略 (网格):**
  * 执行入口: `/root/trader_bot/run_grid_bot.py`
  * 服务配置: `/etc/systemd/system/bot-grid.service`


* **Martin 策略 (马丁):**
  * 执行入口: `/root/trader_bot/run_martin_bot.py`
  * 服务配置: `/etc/systemd/system/bot-martin.service`


* **Signal 策略 (信号):**
  * 执行入口: `/root/trader_bot/run_signal_bot.py`
  * 服务配置: `/etc/systemd/system/bot-signal.service`



### 2. 常用运维命令（免拼接，直接复制）

**🟢 Grid 策略 (网格机器人)**

* **重启/停止/状态:** `systemctl restart bot-grid` | `systemctl stop bot-grid` | `systemctl status bot-grid`
* **查看实时日志/报错:** `  journalctl -u bot-grid -n 100 -f    `

**🔵 Martin 策略 (马丁机器人)**

* **重启/停止/状态:** `systemctl restart bot-martin` | `systemctl stop bot-martin` | `systemctl status bot-martin`
* **查看实时日志/报错:** `        journalctl -u bot-martin -n 100 -f        `

**🟣 Signal 策略 (信号机器人)**

* **重启/停止/状态:** `systemctl restart bot-signal` | `systemctl stop bot-signal` | `systemctl status bot-signal`
* **查看实时日志/报错:** `       journalctl -u bot-signal -n 100 -f       `

### 3. 核心注意事项

* **配置重载:** 每次修改了 `/etc/systemd/system/` 下的 service 文件后，必须先执行 `systemctl daemon-reload`，再执行 restart。
* **内存分配策略 (已放宽限制):**
  * 依托于 `2GB 物理内存 + 2GB 虚拟内存` 的配置，为避免机器人运行中被误杀，当前 3 个服务均设置了 **`MemoryMax=1200M`**。
  * 三者合计理论峰值为 3600M，在 4GB 总容量的安全范围内。
  * 配合 `Restart=always` 与 `RestartSec=5` 参数，即使偶发 OOM 也能在 5 秒内迅速自启。
* **一键排查进程被杀记录 (OOM检查):**
```bash
dmesg -T | grep -i -E "killed process|oom" -C 5
```

## 五、 本地 MongoDB 数据库服务运维

本服务已配置与本地 Windows 完全一致的环境，供本机的爬虫、商城后端（`easy-shop`）等服务直接以 `localhost` 免修改调用。

### 1. 核心信息与配置路径

| 模块 / 配置项 | 路径或对应值 | 说明 |
| --- | --- | --- |
| **系统服务名称** | `mongod.service` | 系统 Systemd 托管服务 |
| **主配置文件** | `/etc/mongod.conf` | 管理端口、监听地址（仅 `127.0.0.1`）与鉴权开关 |
| **数据持久化路径** | `/var/lib/mongodb` | 数据库实际文件存放目录 |
| **日志文件路径** | `/var/log/mongodb/mongod.log` | 运行及报错排查日志 |
| **监听端口** | `27017` | 绑定本地，不对公网开放 |
| **授权用户** | `localUser` | 所属鉴权库 `admin`，拥有 `root` 权限 |
| **用户密码** | `localPassword123` |  |
| **业务数据库** | `crawler_data` | 爬虫与商城默认商品/订单数据存放库 |

### 2. 常用运维命令与连接方式

* 🟢 **服务启停与状态检查:**
```bash
systemctl restart mongod
systemctl stop mongod
systemctl status mongod
```

* 🔍 **查看实时运行日志:**
```bash
tail -n 100 -f /var/log/mongodb/mongod.log
# 或通过 systemd 查看
journalctl -u mongod -n 50 -f
```

* 🚀 **终端直连命令 (Mongosh 交互式进入):**
```bash
mongosh "mongodb://localUser:localPassword123@localhost:27017/?authSource=admin"
```

* 🐍 **Python / 代码直连配置与 URI:**
```python
# 连接 URI 与本地完全一致，代码直接复用：
MONGO_URI = "mongodb://localUser:localPassword123@localhost:27017/?authSource=admin"
MONGO_DB_NAME = "crawler_data"

# PyMongo 示例：
# from pymongo import MongoClient
# client = MongoClient(MONGO_URI)
# db = client[MONGO_DB_NAME]
```

* 💾 **本地历史数据同步（如需导入/备份）:**
```bash
# 1. 导出指定业务库数据 (在存有旧数据的机器上执行)
mongodump --uri="mongodb://localUser:localPassword123@localhost:27017/crawler_data?authSource=admin" --out=./mongo_backup

# 2. 导入恢复数据至当前服务器 (在服务器上执行)
mongorestore --uri="mongodb://localUser:localPassword123@localhost:27017/?authSource=admin" ./mongo_backup
```

## 六、 常见故障排查 (避坑指南)

### 🚨 故障 1：前端更新后浏览器依旧白屏 / 无法显示新功能

* **根本原因：** Cloudflare 边缘节点或浏览器存在“死缓存”。
* **解决方案：**
  1. 登录 Cloudflare 控制台 -> Caching (缓存) -> Configuration -> 点击 **`Purge Everything`**。
  2. 浏览器端按 `Ctrl + F5` 强制刷新，或在 F12 Network 中勾选 `Disable cache`。



### 🚨 故障 2：机器人突然不交易了 / 服务状态显示 failed 或 killed

* **根本原因：** 极大概率是内存溢出（OOM），导致系统强制杀死了 Python 进程。
* **解决方案：**
  1. 执行 `dmesg -T | grep -i oom` 确认是否是因为内存不足。
  2. 检查是哪个策略吃内存：`systemd-cgtop`。
  3. 虽然内存限制已放宽至 1200M，但如果持续出现 OOM，建议排查 Python 代码中是否存在内存泄漏。



### 🚨 故障 3：商城访问返回 429 Too Many Requests 或转链生成失败

* **根本原因：**
  1. 接口触发了 Nginx 的防刷防御机制（单个 IP 针对转链或登录接口请求频次超过了 2次/秒）。
  2. 拼多多凭据配置错误、PID 格式异常，或本地 `config.local.json` 发生语法错误。
* **解决方案：**
  1. 如属于正常测试时的手速过快，等待 2~3 秒冷却后即可自动恢复正常；如需放宽限制，可调整 `/etc/nginx/sites-available/easy-shop` 中的 `rate` 与 `burst`。
  2. 执行 `journalctl -u easy-shop.service -n 50 -f` 查看报错堆栈。
  3. 执行自检命令验证配置有效性与 Mongo 连通性：
     ```bash
     /root/easy_shop_web/mobile_web/venv/bin/python /root/easy_shop_web/mobile_web/run.py --check-mongo
     ```
  4. 修改了 `config.local.json` 后，必须执行 `systemctl restart easy-shop.service` 使配置生效。
