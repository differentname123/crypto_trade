### 全链路智能内容引擎架构方案

本架构采用严格的“需求定义 ➔ 基座支撑”闭环逻辑。先由顶层应用层定义具体的数据依赖，底层的三步处理管线则完全围绕这些依赖进行数据降维、存储与精准拼装。

---

### 一、 顶层应用层：定义生成目标与数据依赖 (Application Layer)

只需更换 Prompt，即可无限扩展应用。每个应用场景都会向底层基座提出极其具体的数据依赖：

* **应用 A：专业研报融合（多对一）**
* **核心需求**：交叉比对多源线索，生成客观严谨的分析。
* **底层依赖**：① 绝对精确的**时间戳**与**领域实体**（防过期、防跨区）；② 100% 准确的**原始图表数据**（防大模型幻觉）；③ 完整的“图文佐证链”（观点后必须跟原配图）。


* **应用 B：流量爆款二创（一对一）**
* **核心需求**：锁定爆点，放大情绪，生成高转化网感贴。
* **底层依赖**：① 高**互动指标**（点赞/转发量，用于证明其具备爆款潜质）；② 原汁原味的**原始文本**（提取真实网友情绪与黑话）。


* **应用 C：情绪预警雷达（N 对一）**
* **核心需求**：监控特定事件/币种的极端舆论走向。
* **底层依赖**：① 细颗粒度的**时间窗口**切分；② 特定**领域实体**的定向检索。



---

**为了完美支撑上述应用依赖，底层数据基座按以下 3 步构建逻辑闭环：**

### 二、 基座 Step 1：统一结构化层 (数据降维与提取)

**设计逻辑**：利用多模态大模型（VLM），将杂乱的原贴强制转化为“纯线性流 JSON”。**这个 JSON 的每一个字段，都是为了满足应用层的数据依赖而设计的。**

**【核心示例：最终统一 JSON 格式】**

```json
{
  "post_metadata": {
    "post_id": "88472910",
    "publish_timestamp": "2026-07-27T10:00:00Z", // 支撑应用A、C的时间范围依赖
    "engagement_metrics": {
      "likes": 5200, // 支撑应用B的“爆款潜质”过滤依赖
      "shares": 800
    }
  },
  "global_analysis": {
    "domain_entities": ["BTC", "美联储降息"] // 支撑应用A、C的“精准领域定向”依赖
  },
  "content_stream": [
    {
      "index": 1,
      "type": "text",
      "raw_text": "昨晚这波暴跌真的麻了，看清算图，大户都在跑路！", // 保留原汁原味情绪，支撑应用B
    },
    {
      "index": 2,
      "type": "image",
      "media_placeholder": "<img_source_88472910_idx_2>", // 物理占位符，支撑应用A插入原图
      "visual_description": "一张全网爆仓清算热力图，红色区域集中在64000美元下方。", 
      "ocr_text": "Liq: $450M, Short: 80%, Long: 20%" // 提取死数据，支撑应用A的“防幻觉客观数据”依赖
    }
  ]
}

```

### 三、 基座 Step 2：拆解入库层 (双路存储引擎)

**设计逻辑**：严禁将完整 JSON 向量化。必须按“过滤属性”和“语义属性”拆分为两路存储，为后续的高精检索打地基。

1. **标量库 (Metadata SQL)**：
* **存什么**：剥离 JSON 中的 `publish_timestamp`、`engagement_metrics`、`domain_entities`。
* **目的**：为应用层提供**绝对阻断式过滤**。例如应用 B 可以在此直接过滤出 `likes > 5000` 的数据。


2. **向量库 (Vector Database)**：
* **存什么**：将 `content_stream` 中的人类语言（`raw_text`、`visual_description`、`ocr_text`）进行切片（Chunking），通过向量模型（如 BGE-M3）转化为高维向量。
* **目的**：每个向量强制绑定原贴 ID 与 `index` 序号，支撑后续应用层的语义模糊搜索。



### 四、 基座 Step 3：动态组装层 (检索与上下文拼装)

**设计逻辑**：接收应用层的具体指令，去数据库中执行“过滤 ➔ 匹配 ➔ 连带抓取”，最终拼装成干净的 Context 交给 LLM 生成。

**闭环工作流示例（以应用 A：专业研报形成为例）**：

1. **硬性过滤 (满足时间/实体依赖)**：在标量库中执行 `timestamp > 昨天` AND `domain_entities 包含 'BTC'`。剔除所有过期和无关数据。
2. **语义召回 (满足内容匹配)**：在过滤范围内，向向量库检索“链上清算异动”，精准命中上述 JSON 示例中的 `index: 1`（文本）和 `index: 2`（图片描述）。
3. **相邻节点补全 (满足证据链依赖)**：系统发现 `index: 1` 是文本结论，自动抓取并绑定与其相邻的 `index: 2`（图片占位符与 OCR 数据）。
4. **最终投喂**：将这段“带有强时间标记 + 客观 OCR 数据 + 原图占位符”的优质积木喂给生成大模型，大模型即可严格按照研报 Prompt，输出一篇数据精准、图文并茂的专业分析，**至此完成整个业务与数据的逻辑闭环。**
